# Security fixes: deployment and session behavior

This patch addresses C-1, C-2, and H-1 through H-5 from the security review.

- Secret reads, updates, deletes, bulk deletes, and usage events are scoped to the authenticated user. Master-password changes reject foreign/missing/duplicate secret IDs and invalid device challenges before changing any data.
- Device enrollment rechecks persisted approval, rejection, and IP blocking inside a transaction, binds the challenge to its user/device, and serializes enrollment-secret rotation across concurrent attempts.
- Reset email links use the configured `BACKEND_URL` origin (default `https://api.authier.pm`), never request headers. Configure this to the backend that serves `/confirm-master-device-reset`; local development may use an HTTP localhost origin.
- Autofill uses the public suffix list, including private suffixes, with a DNS label boundary. Lookalike domains and separate hosted tenants do not share credentials.
- Access tokens stay in memory or privileged extension `storage.session`; refresh tokens are renewed using an HttpOnly cookie. Plaintext JWTs and raw vault keys are never written to localStorage/browser.storage.local.
- Unlocked vault keys stay in page memory (web vault) or privileged, in-memory `browser.storage.session` (extension). Background-worker restarts keep the extension session; a browser restart requires an explicit unlock. No raw key, plaintext enrollment secret, PRF output, or wrapping CryptoKey is written to persistent browser storage.
- Optional passkey unlock uses WebAuthn PRF with required user presence and verification. A compatible device authenticator or security key supplies the secret; HKDF-SHA-256 derives an AES-GCM wrapping key. IndexedDB stores only the wrapped master key and public metadata, authenticated as additional data. The passkey must be stored outside Authier. A stolen browser profile alone cannot evaluate the authenticator's PRF, even if copied while Authier is unlocked. Master-password unlock remains available when the browser/authenticator lacks PRF support.
- Explicit lock discards live keys and invalidates outstanding unlock/setup requests. Logout removes passkey-unlock configuration; changing the master key invalidates it. The extension retains an allowlisted, password-encrypted local snapshot and encrypted pending saves for offline unlocking. The web vault rechecks server device approval after passkey unlock.
- The old `authier-device-vault` store persisted a WebCrypto wrapping key alongside its ciphertext. The non-exportable flag did not protect a copied profile, and overwriting a record or calling IndexedDB.deleteDatabase left recoverable key bytes in Chromium's LevelDB files. Upgrade cleanup removes the extension's own IndexedDB files with a strictly scoped browsingData call; the web vault uses a same-origin POST returning Clear-Site-Data from its own Worker. Firefox removes its per-database SQLite file. A keyless version-2 tombstone prevents old tabs recreating the unsafe store. Failed cleanup blocks use of the updated vault until it succeeds.
- Cleanup of the current store does not sanitize filesystem snapshots, backups, unallocated disk space, or historical plaintext storage from older versions. Previously copied keys and exposed credentials require rotation. These changes do not protect against code executing inside an unlocked vault, a compromised authenticator, or a fully compromised operating system. Passkey-provider storage and biometric/PIN support depend on the user's platform.
- The web and extension clients generate enrollment secrets with cryptographic randomness. New server verifiers use PBKDF2-HMAC-SHA-256 with a random 128-bit salt and 600,000 iterations, checked in constant time. Hosted Cloudflare Workers reject native PBKDF2 calls above 100,000 iterations; the server uses a portable fallback for that specific error while retaining the 600,000-round format and verifying existing hashes unchanged. The server never stores the submitted plaintext enrollment secret.

## Database rollout

The generated migration is `backend/drizzle/migrations/20260906225610_dashing_mulholland_black/migration.sql`. It renames `User.addDeviceSecret` to `addDeviceSecretHash` and converts existing values to SHA-256 verifiers. Existing accounts remain usable; successful enrollment/password changes rotate to fresh secrets stored in the salted PBKDF2 format. There is no plaintext-verifier fallback.

Apply the migration manually as part of a coordinated backend deployment: the old backend expects the old column, while the new backend expects the renamed column. This patch does not run migrations against deployed databases. Migration compatibility is tested in PGlite.

These changes prevent the reported exploit paths. They cannot undo exposure of credentials or keys from an earlier compromise; previously exposed credentials need rotation.
